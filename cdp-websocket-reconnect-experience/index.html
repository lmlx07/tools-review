CDP WebSocket 断线重连实战：应对 ConnectionAbortedError

发表于2026-06-09|更新于2026-06-09|CDP 实战经验分享
|浏览量:

一句话总结：CDP 的 WebSocket 连接在长时间运行时可能因安全软件拦截、页面导航、浏览器资源紧张而断开。解决之道是建立”操作前心跳检测 → 断开自动重连 → 重试当前操作”的防御性编程模式。

问题现象

在运行自动化脚本时，控制台突然输出：

此时脚本崩溃，之前的进度全部丢失。需要从头开始运行。

这个问题在长时间运行的脚本中（如批量上传 100 章内容，总耗时 30+ 分钟）尤其常见。

断线原因分析

根据实际排查，常见原因按概率排序：

1. 安全软件拦截（最高概率）

360、腾讯管家等安全软件将本地 WebSocket 连接误判为威胁，主动切断连接。

特征：运行一段时间后随机断开，没有固定规律。

验证方法：检查安全软件的日志，看是否有”拦截网络攻击”之类的记录。

2. 页面导航导致 target 短暂不可用

当 CDP 发 Page.navigate 导航到新页面时，Chrome 会短暂断开旧的 WebSocket 连接然后重建。

特征：断线总发生在 Page.navigate 调用或页面跳转之后。

3. 浏览器资源紧张

浏览器长时间运行后内存占用上升，Chrome 可能主动回收资源。

特征：运行多小时后出现，伴随浏览器变慢。

4. Windows 电源管理

Windows 将浏览器进程挂起或降级优先级。

特征：电脑锁屏或屏幕关闭后出现。

总结

问题 解决方案
安全软件断连 加入白名单 + 自动重连兜底
导航后断开 navigate_and_rebind 等待就绪
浏览器资源紧张 控制频率 + 内存监控

核心策略：不要试图完全避免断线（不可能），而是建立”操作前检查 → 断开自动重连 → 重试当前操作”的防御模式。配合安全软件白名单和合理的操作频率，可以将断线对自动化流程的影响降到最低。
