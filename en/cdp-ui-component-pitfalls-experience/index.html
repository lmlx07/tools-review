Three Common Traps in UI Library Automation: A Component Library Case Study

Created2026-06-09|Updated2026-06-09|CDP PracticeExperience Sharing
|Post Views:

Summary in one sentence: UI component libraries typically hide the original input element and replace it with custom DOM elements, then listen for events on the container. To automate them, click the outer container (label/div) instead of the hidden input, and sometimes you need to simulate the full event chain.

Trap 1: Radio Buttons

Key points:

  1. The input[type=radio] is hidden
  2. The library doesn’t use the raw input’s change event
  3. Clicking <label> triggers the library’s internal state management

Universal Principles

1. Click Outer Container, Not Inner Elements

2. Search by Text, Not by Structure

Structural selectors (nth-child, class combinations) are fragile — version upgrades or theme changes can alter class names.

3. Use offsetParent !== null to Filter Visible Elements

Component libraries often pre-render popups and panels in the DOM even when invisible:

Debugging Checklist

When a click doesn’t work:

  1. Inspect element structure: Get outerHTML
  2. Check visibility: el.offsetParent !== null
  3. Try layered approach: Outer container → CDP click → Full event chain
Component Wrong Approach Correct Approach
Radio button Click hidden input Click label container
Custom Select Set value property Click trigger → select option
Switch Set checked property Click container element
Custom Dropdown Direct value assignment CDP mouse open → select → Escape

Core principle: With UI library components, always click the outermost visible container. When JS click fails, escalate to CDP’s dispatchMouseEvent for real event injection.
