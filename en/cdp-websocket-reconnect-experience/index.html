CDP WebSocket Reconnection: Handling ConnectionAbortedError in Practice

Created2026-06-09|Updated2026-06-09|CDP PracticeExperience Sharing
|Post Views:

Summary in one sentence: CDP WebSocket connections can drop due to security software, page navigation, or browser resource pressure. The solution: a “heartbeat before each operation → auto-reconnect on disconnect → retry current operation” defensive pattern.

The Problem

During long-running automation, the console suddenly shows:

The script crashes and all progress is lost. This is especially common in batch operations (e.g., uploading 100 chapters over 30+ minutes).

Root Cause Analysis

1. Security Software Interception (Most Likely)

360, Tencent PC Manager, and similar security tools may flag local WebSocket connections as threats.

Symptoms: Random disconnects with no fixed pattern.

2. Page Navigation

When CDP sends Page.navigate, Chrome briefly disconnects the old WebSocket and reconnects.

Symptoms: Disconnects always happen after Page.navigate calls.

3. Browser Resource Pressure

Chrome may reclaim resources after running for long periods with high memory usage.

4. Windows Power Management

The browser process gets suspended or its priority is lowered.

Summary

Issue Solution
Security software disconnection Whitelist + auto-reconnect fallback
Navigation drops Wait for readyState after navigation
Browser resource pressure Control pace + monitor memory
Power management Adjust Windows power settings

Core strategy: Don’t try to prevent disconnections entirely (impossible). Instead, build a “check before each operation → auto-reconnect → retry” defensive pattern. Combined with security software whitelisting and reasonable operation pacing, you can minimize disruption to your automation flow.
