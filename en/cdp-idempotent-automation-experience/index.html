Idempotent Automation Design: Resume Interrupted Scripts Without Duplication

Created2026-06-09|Updated2026-06-09|CDP PracticeExperience Sharing
|Post Views:

Summary in one sentence: Idempotent automation means the script is “re-entrant” — no matter where it crashes or how many times you retry, the final state is the same. Implementation: scan completed work before starting → process only unfinished items → persist progress after each item.

The Problem

You need to batch-upload 100 chapters to a novel platform. Each chapter’s workflow:

The whole process takes 30~60 minutes. Crashes happen.

If the script crashes at chapter 57, re-running should:

  • Not duplicate: Chapters 1~56 already published → skip them
  • Not skip: Chapter 57 was interrupted → resume or skip if already done
  • Self-heal: Recover from last known state if records are lost

Core Concept

Idempotency means: no matter how many times the script crashes and restarts, the end result is the same.

Idempotent vs Non-Idempotent Operations

Operation Idempotent? Notes
Click “Next” button ❌ Clicking twice submits twice
Fill input field ✅ Same value, same result
Select radio ✅ Same selection, same result
Click “Confirm Publish” ❌ May create duplicates
Navigate to URL ✅ Same URL, same page
Read page data ✅ Read-only, naturally idempotent
Write progress file ✅ Overwrite, not append

Non-idempotent protection: Verify if the action was already performed before executing.

Summary

  1. Idempotent design isn’t a post-hoc patch — plan it from the start
  2. Triple safeguard: local record + page verification + exception retry
  3. Non-idempotent operations need guards: check state before executing
  4. Connection errors deserve special handling: reconnect and retry the current item
  5. Persist immediately: write after each item, not in batch at the end

Summary: Idempotent design upgrades automation scripts from “fragile one-shot tools” to “robust long-running services.” The concept is simple — check “what’s already done” before starting, rather than assuming “nothing is done.” Combined with persistent records and page state verification, even with network issues, browser crashes, or security software interruptions, the script runs reliably to the end.
